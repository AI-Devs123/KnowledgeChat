# RAG 检索优化工作流程

## 📋 评估驱动开发流程

```
┌─────────────────────────────────────────────────────────────────┐
│                    评估驱动开发 (EDD) 流程                        │
└─────────────────────────────────────────────────────────────────┘

步骤 1: 准备测试集
├─ 收集真实用户查询
├─ 标注期望文档
└─ 保存到 test_queries.json
    │
    ↓
步骤 2: 建立 Baseline
├─ 运行原始检索方法 (ensemble)
├─ 记录性能指标
└─ 保存到 baseline.json
    │
    ↓
步骤 3: 测试优化方案
├─ 逐个测试新检索策略
│   ├─ vectorstore (纯向量检索)
│   ├─ adaptive (自适应检索)
│   ├─ hybrid_fusion (RRF 融合)
│   └─ rerank (重排序)
├─ 与 Baseline 对比
└─ 计算改进百分比
    │
    ↓
步骤 4: 分析结果
├─ 生成对比报告
├─ 找出最佳方案
└─ 输出改进建议
    │
    ↓
步骤 5: 应用优化
├─ 修改配置文件
├─ 部署到生产环境
└─ 持续监控效果
```

### 标准评估流程

1. **建立 Baseline**
   - 使用现有的 `ensemble` 混合检索
   - 运行完整测试集
   - 保存性能指标作为基准

2. **测试优化方案**
   - 逐个测试新的检索策略
   - 每次都与 Baseline 对比
   - 记录改进百分比

3. **选择最佳方案**
   - 综合考虑 F1、响应时间等指标
   - 选择改进最明显的方案
   - 应用到实际系统

## 📊 评估指标说明

| 指标 | 含义 | 理想值 |
|------|------|--------|
| **Precision** | 检索结果的准确性 | 越高越好 |
| **Recall** | 相关文档的覆盖率 | 越高越好 |
| **F1 Score** | Precision 和 Recall 的综合 | 越高越好 |
| **MRR** | 首个相关文档的排名 | 越高越好 |
| **响应时间** | 检索耗时 | 越低越好 |

## 🔄 迭代优化建议

如果某个方案表现不佳：
1. 检查测试集是否足够代表真实场景
2. 调整参数（top_k, score_threshold）
3. 分析失败案例，针对性改进
4. 考虑组合多种策略

如果所有方案都不如 Baseline：
1. Baseline 可能已经足够好
2. 扩充测试集，增加边界案例
3. 考虑启用重排序模型（rerank）
4. 优化 Embedding 模型

## 💡 实践建议

1. **测试集质量 > 数量**: 20个高质量样本 > 100个随机样本
2. **关注业务指标**: 根据实际场景选择最重要的指标（精确率 vs 召回率）
3. **平衡性能与效果**: 响应时间也是重要考量
4. **A/B 测试验证**: 线上小流量测试再全量推广
